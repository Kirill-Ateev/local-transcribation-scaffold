# Design: local-voice-transcription-stack

## Context

Проект создаётся с нуля в пустом репозитории. Железо и роли зафиксированы в proposal.md: DGX Spark (GB10: ARM64, Blackwell sm_121, 128 ГБ unified memory, DGX OS на базе Ubuntu 24.04 с NVIDIA AI stack) — сервер инференса; MacBook — клиент диктовки на базе готового OpenWhispr. Ключевое ограничение платформы: свежесть CUDA-стека для sm_121 делает совместимость готовых ускоренных рантаймов главным техническим риском, поэтому выбор рантайма проверяется спайком до остальной работы.

Решения по UX, принятые владельцем проекта: только батч (без стриминг-partials); без LLM-постобработки (пунктуацию даёт сама модель семейства Whisper); устройства используются последовательно, но длинная транскрибация аудио нужна уже в первой версии.

## Goals / Non-Goals

**Goals:**

- Один синхронный OpenAI-совместимый эндпоинт, покрывающий и диктовку (< 10 c аудио), и часовые записи.
- Рантайм faster-whisper на GPU GB10 с подтверждённым использованием CUDA (не тихий CPU-фолбэк).
- Полный путь «хоткей → текст в курсоре» за ≤ 3 c медианы на LAN для коротких фраз.
- Воспроизводимая оценка качества RU+EN-терминов (eval-набор + WER/CER) как критерий приёма и регрессии.

**Non-Goals:**

- Стриминговые частичные результаты во время речи.
- LLM-чистка текста, команды форматирования, диаризация, таймкоды в UI клиента.
- Одновременная многопользовательская нагрузка, батчинг запросов, квантизация ради throughput.
- Несколько моделей в памяти и переключение моделей по запросу — резидентна только large-v3 (экономия ресурсов).
- Удалённый доступ вне локальной сети: VPN (Tailscale/WireGuard), reverse-proxy, TLS — сервис только для домашней LAN.
- Поддержка моделей вне семейства Whisper (GigaAM и др.) — возможное будущее расширение, не эта версия.

## Decisions

### D1. Рантайм: Docker-рецепт `paruparu/faster-whisper-dgx-spark` — целевой путь

Целевой сервер на DGX Spark — окружение из рецепта: контейнер на базе
`nvidia/cuda:12.4.1-cudnn-devel-ubuntu22.04`, где CTranslate2 v4.6.2 собирается
из исходников с CUDA (pip-CPU версия подменяется), `entrypoint.sh` настраивает
`LD_LIBRARY_PATH` для cublas/cudnn; хостовой CUDA 13 не трогается. Это снимает
главный риск платформы — несовместимость готовых pip-колёс CT2 со sm_121.

Интеграция: штатный `server.py` рецепта (эндпоинты `/transcribe`, `/health`)
используется только для смоука рантайма; целевой сервис — наш FastAPI-код,
запускаемый внутри того же контейнера через override команды
(`deploy/docker-compose.spark.yml` монтирует `server/`). Так сохраняются
требования спек: OpenAI-совместимый эндпоинт, токен, VAD, длинные аудио.

Фолбэк-лестница при провале рецепта:

1. Собственное окружение venv + systemd (вариант B) — тот же код, но pip-CT2
   на GB10 может дать только CPU.
2. `whisper.cpp` из исходников с `GGML_CUDA=ON`.
3. HF Transformers / NeMo на PyTorch aarch64 wheels.

Альтернатива «сразу писать на чистом Transformers» отклонена: теряем 2–4× скорость faster-whisper при том же качестве.

### D2. Модель: единственная резидентная Whisper large-v3

Разворачивается ровно одна модель — large-v3 (MIT, встроенная пунктуация, что закрывает отказ от LLM-слой). Turbo-вариант не разворачивается: каждая резидентная модель держит веса в unified memory, а второй вариант не даёт качественного выигрыша — при желании ускориться проще вернуться к этому решению позже. Параметр запроса `model` принимается для совместимости с OpenAI-протоколом (клиенты шлют его всегда) и игнорируется как селектор. Параметры декодирования для диктовки: `condition_on_previous_text=False` (независимые короткие фразы — против зацикливания галлюцинаций), температурный фолбэк по умолчанию faster-whisper. Словарь терминов через `initial_prompt` — опция конфига, тестируется eval-набором.

Альтернатива «large-v3 + turbo с ленивой загрузкой» отклонена владельцем проекта ради экономии памяти и простоты; цена — латентность всегда на уровне полной модели, что проверяется замером (см. Risks).

### D3. API: один синхронный эндпоинт, сериализованная обработка

FastAPI + Uvicorn, один воркер, владеющий моделью. Очередь запросов FIFO: при одновременных запросах второй ждёт завершения первого. Это соответствует паттерну использования (устройства по очереди) и исключает гонки за GPU-память. Длинные аудио обрабатываются в том же запросе: Silero VAD режет запись на речевые сегменты (≤ 30 c, малый оверлей), сегменты транскрибируются последовательно, текст склеивается. Память ограничена размером сегмента, а не файла. Асинхронные джобы сознательно отложены: клиенты длинных файлов — curl/CLI с большим таймаутом.

Альтернативы: отдельный асинхронный jobs-API (отложено как YAGNI), параллельные воркеры (лишняя сложность без конкурентной нагрузки).

### D4. Клиент: OpenWhispr без форка, custom provider → Spark

Используем штатную поддержку custom provider (base URL + Bearer). Ноль своего клиентского кода в этой версии. Спайк-проверка протокола (multipart-форма, заголовки, таймауты) входит в ранние задачи; если несовместимость фатальна — фолбэк: Handy с custom endpoint либо минимальный форк (решение принимается по факту спайка, код клиента остаётся вне этого change).

Вставка в терминал: без автонажатия Enter — это поведение самого клиента, фиксируем в инструкции настройки.

### D5. Безопасность и сеть: Bearer-токен, минимум инфраструктуры

Токен в переменной окружения/`.env` вне git; генерация описана в deploy-инструкции. Сервис слушает интерфейс локальной сети; проброс портов на роутере не настраивается — доступ возможен только из домашней LAN. Никакой дополнительной сетевой инфраструктуры (VPN/Tailscale, reverse-proxy, TLS) сознательно не разворачивается: трафик ходит внутри доверенной сети, а каждый лишний компонент — это обслуживание и точки отказа.

Альтернатива «VPN/TLS сразу» отклонена как избыточная для сценария «диктовка дома»; при появлении потребности в удалённом доступе это отдельное решение, расширяющее deployment-спеку.

### D6. Упаковка: A — Docker рецепта (основной), B — venv+systemd (альтернатива)

Решение зафиксировано владельцем заранее, без ожидания спайка: целевой способ
— docker compose из рецепта D1 (`deploy/docker-compose.spark.yml`: сборка их
Dockerfile, монтаж нашего кода, volume под веса, restart always, GPU-device
stanza). Альтернатива «на всякий случай» — venv + systemd unit
(`deploy/transcribe.service`, `Restart=always`, автозапуск): отладка на CPU,
работа без Docker, запасной путь если рецепт недоступен. Оба варианта
описаны в `deploy/README.md`.

### D7. Eval-харнесс: фиксированный набор фраз + офлайн-скоринг

`eval/phrases.yaml`: ~30 фраз трёх классов (чистый RU; RU с EN-терминами вида «kubectl», «Cursor», «deploy»; числа/идентификаторы), эталонные расшифровки вручную. `eval/score.py`: прогон набора через API, подсчёт WER/CER, сравнение конфигураций сервиса (с initial_prompt и без). Артефакты прогонов сохраняются для регрессии. Это инструмент приёмки требований по качеству, не пользовательский функционал.

## Risks / Trade-offs

- [Репозиторий D1 заброшен/не работает на конкретном DGX OS] → спайк первым делом; лестница фолбэков D1; результаты фиксируются в `docs/spike-runtime.md`.
- [CTranslate2 соберётся, но молча возьмёт CPU] → smoke-check проверяет загрузку CUDA в логах и время инференса; health показывает бэкенд.
- [Custom provider OpenWhispr несовместим (таймаут/заголовки)] → ранний спайк клиента до написания серверного «полированного» кода; фолбэк Handy/форк.
- [Wi-Fi добавляет джиттер к латентности] → замер латентности отдельно по Ethernet и Wi-Fi; рекомендация Ethernet для Spark в deploy-доках.
- [Отказ от turbo: полная large-v3 может не уложиться в целевую латентность диктовки на GB10] → замер в задаче 5.5 до приёмки; если медиана > 3 c — вернуться к вопросу о втором варианте модели (осознанное расширение, не молчаливое).
- [Галлюцинации Whisper на тишине/шуме несмотря на VAD] → пороги VAD, `no_speech_threshold`, `condition_on_previous_text=False`; кейс покрыт сценарием спеки.
- [Синхронный запрос на часовой файл рвётся по таймауту клиента] → документировать большие таймауты curl (`--max-time`); при реальной боли — будущий jobs-API (вне текущего скоупа).

## Migration Plan

Greenfield: порядок ввода — спайк рантайма (D1) → каркас сервиса + smoke-check → клиент (спайк провайдера) → eval-набор → deploy-упаковка (systemd) → приёмка по спекам. Шаги спайка, развёртывания и приёмки выполняются владельцем на целевом железе отдельно; задачи change ограничены кодом, инструментами и проверяемыми здесь верификациями. Откат тривиален: остановить юнит, удалить venv; данные состояния нет (сервис stateless, кроме резидентной модели).

## Open Questions

- Итоговая проверка рецепта на живом GB10 (device=cuda в `/health`) — выполняет владелец при тестировании; в репозитории зафиксирована интеграция (compose, инструкции).
- Значение порта — фиксируется при реализации, на дизайн не влияет.
